curve-lab · the tunnel

The tunnel: one URL for the phone, for good

A named Cloudflare tunnel gives the Astro app a hostname that does not change, on your own domain, while the Mac is awake. It is not hosting: when the Mac sleeps or the tunnel stops, the URL stops answering.

The workbench pages are already served inside the app (/pages/<file>), so the whole hub works through the tunnel — no second port, no second server.

What only you can do: authorise the tunnel against your Cloudflare account (cloudflared tunnel login) and choose the hostname. Everything else is a command.

Quick tunnel, while there is no domain

No domain, no account, no config — and a different address every time:

~/bin/cloudflared tunnel --url http://localhost:4321

It prints https://<three-words>.trycloudflare.com; open that on the phone. Start the app first (cd app && npm run dev -- --host), or the tunnel has nothing to serve. Stop it with Ctrl-C, or

pkill -f "cloudflared tunnel --url"

The address dies with the process. That is the whole trade: instant, free, temporary. For a name that lasts, do the one-time setup below.

Before you start: the account needs a zone. cloudflared tunnel login shows a list of domains to authorise against. With no domain on the account the list is empty, the login sits "Waiting for login…" for about eight minutes and then fails with Failed to fetch resource — it has nothing to authorise, and no cert.pem is written (or your browser downloads one, which you would have to copy to ~/.cloudflared/cert.pem by hand). Add a domain to the Cloudflare account first — the free plan is enough, and Registrar sells one at cost.

One-time setup

Four commands, in order, from the repo root.

~/bin/cloudflared tunnel login

The browser opens. Pick the domain (zone) you want the lab on and press Authorize. It writes ~/.cloudflared/cert.pem; that file is your account credential and is never committed.

~/bin/cloudflared tunnel create curve-lab

It prints a UUID and writes ~/.cloudflared/<UUID>.json. That JSON is the tunnel's own key: never commit it, never paste it.

~/bin/cloudflared tunnel route dns curve-lab lab.example.com

Use the real hostname, for example lab.curvelab.dev. This is the line that makes the address permanent: it creates the CNAME in Cloudflare's DNS.

cat > ~/.cloudflared/config.yml <<'YAML'
tunnel: curve-lab
credentials-file: /Users/thomaskelly/.cloudflared/<UUID>.json

ingress:
  - hostname: lab.example.com
    service: http://localhost:4321
  - service: http_status:404
YAML

Replace <UUID> and the hostname. The last rule is the catch-all Cloudflare requires.

Get in

Two things must run: the app, and the tunnel.

cd app && npm run dev -- --host

scripts/tunnel.sh start

Then open https://lab.example.com on the phone. scripts/tunnel.sh status prints the hostname and its HTTP code; 200 means end to end.

For iteration, leave npm run dev running. Astro reloads on save, and the tunnel does not notice — it forwards whatever the app serves. A full page refresh on the phone is the reliable check; live-reload over a tunnel is often a second behind.

app/astro.config.mjs allows the tunnel host, and any host named in CURVE_LAB_HOSTS (comma-separated), so Vite does not answer "Blocked request".

Get out

scripts/tunnel.sh stop

That kills the tunnel; the URL stops answering at once. Stop the app with Ctrl-C in its terminal. Nothing is left running in the background.

To stop for a while, that is enough. The DNS record stays; the next start uses it again.

Turning it off for good

Three things exist: the tunnel, its DNS record, and the local config.

  1. Cloudflare dashboard → Zero Trust → Networks → Tunnels → curve-lab → Delete. A deleted tunnel stops working immediately.
  2. DNS → delete the lab CNAME for the chosen domain.
  3. On the Mac: remove ~/.cloudflared/config.yml, the <UUID>.json, and ~/.cloudflared/cert.pem if no other tunnel uses the account.

the page loads but is blank, or 502 the app is not running on :4321 cd app && npm run dev -- --host

login waits, then Failed to fetch resource the account has no zone to authorise against add a domain to Cloudflare, then run cloudflared tunnel login again

Ordinary and robust: the login services

Run both as launchd agents and they start at login, restart when they fall over, and stop belonging to a terminal window. The quick tunnel needs no domain for this.

scripts/service.sh install
scripts/service.sh status
scripts/service.sh url          # prints today's address, and copies it

install writes two agents — com.curvelab.app (the Astro dev server on :4321) and com.curvelab.tunnel (cloudflared tunnel --url, forwarding to it) — then starts them. status prints each one's state and pid, the local HTTP code and the phone's. Logs are /tmp/curve-lab-app.log and /tmp/curve-lab-tunnel.log.

scripts/service.sh restart app  # kick the app only — the phone URL survives
scripts/service.sh restart      # both (a tunnel restart means a new URL)
scripts/service.sh log          # tail both logs
scripts/service.sh uninstall    # stop and remove both agents

What "robust" does and does not buy. launchd restarts a process that dies; it starts both at login; it survives this terminal and any agent session ending. It does not survive the Mac sleeping or shutting down, and it does not keep the address: the quick tunnel takes a new name every time its process restarts, so re-run scripts/service.sh url after a restart. A named tunnel (above) removes that last wrinkle once there is a domain.

If this Mac cannot resolve the address. A quick-tunnel name looked up before Cloudflare has created it is cached as "does not exist" by macOS, so curl says Could not resolve host while the tunnel is fine and the phone loads it. status pins the address and says which case you are in. To clear the cache:

sudo killall -HUP mDNSResponder

What this is not

  • Not hosting. Mac asleep, URL down. For a page that is always up, the app has to be deployed — that is the "going public" task in TODO.md, and it needs the disk-reading routes (/pages/**, /api/plate/**, /book) moved or made static first.
  • Not private. The Astro app has no login, and POST /api/stars writes workbench/starred.json. Anyone with the URL can see the hub and write a star file. That is acceptable while it is your own domain and unlisted; it is not acceptable once the URL is shared.
  • Not a second server. The tunnel forwards to :4321 only. The Python workbench server on :8003 is not exposed, and does not need to be: the hub serves the generated pages itself.
