## What is good here

- **The maths is exact, and the page shows it.** The core measures every curve
  in exact fractions. A "grid" here means the smallest step a point can take
  (like 1/27720 — every position is a whole number of those steps). "Bend" means
  arc length divided by straight-line distance: 1.0 is a straight line, higher
  means the curve bends.
- **A claim is never just believed.** The notebook of achievements (`state/ACHIEVEMENTS-int.md`)
  stores a command next to every claim, so anyone can re-run it and see the
  number again.
- **The files guard themselves.** Every data file says what it is (a "format
  string"), one program reads them, and a check fails loudly when a file appears
  without its label. I watched this catch five files in two days.
- **Anyone can read the data without the database.** The `data/` folder holds a
  plain copy of every table, plus a dictionary that explains every field. The
  checks fail if the copy falls behind the database.
- **The catalogue is becoming the product.** 397 curves, each drawn, each named
  so a reader never has to ask which one is meant. The desk where you say "keep,
  later or reject" is turning those choices into permanent records.
- **The research says what it does not know.** Two searches looked for anyone
  who made these curves before. They report "not found in a search", never
  "nobody has ever done this", and they name the terms the field already uses.
- **The new direction has a rule, not just a mood.** The "prime mover" idea
  drives curves from a point walking a circle by whole-number steps (Pythagorean
  triples, like 3-4-5), so every point stays exact. The note also states the
  catch: a fixed triple never closes the circle perfectly, and the file says
  what to do about that.
- **Work survives a crash.** Backups, a register of past faults with the test
  that keeps each one fixed, and a clear rule about who owns which file.

## What should be fixed — worst first

### 1 · The counting rules disagree with each other

This is the big one. The same curve got **three different answers** for how many
times it crosses itself: 9, 4 and 1, from three different counters. Three
pinned examples are already written down (`c-0262` = 9, `c-0070` = 11, and the
Chebyshev cross = 4). The counting programs should all be checked against those
three numbers, and the ones that disagree should be fixed or thrown out.

Why it matters: the project chooses its "best curves" by this number. If the
number depends on which counter you ask, the catalogue is sorted by noise.

### 2 · The saved copy falls behind while people work

The big check failed today for this reason alone: rows were saved while the
check ran, so its copy of the data was already old. The fix is order, not
leniency: refresh the copy at the start of every check, and again just before
saving a version.

### 3 · The sandbox page draws nothing

The sandbox page lost its drawings because two people gave one file two
different jobs. The desk's choices now live there, and the sandbox drawings used
to. The fix is a decision: which file holds what, and then both pages read their
own file. It is already written down in the mail as a question; it needs an
answer, not a guess.

### 4 · The full check takes five minutes

Three of the page checks take 100–146 seconds each. A session that wants to
confirm one small change waits for all of them. The fix: split the slow drawing
from the logic being tested, or remember the heavy work between runs.

### 5 · Some files have never been saved

59 files (including the newest web pages) exist only on this machine. Saving
them is waiting on a decision about who owns them. It is a real risk: a crash
now loses the newest part of the app.

### 6 · Three versions are not on the backup copy

They are waiting for a yes from you. The rule in the notebook says a red or
stale backup is worse than a small delay, because it is the copy you rebuild
from.

### 7 · A rebuilt page can quietly lose its "draft A" label

Two pages dropped the label when they were rebuilt. The label was put back by
the stamping tool, but the real fix is in the builders, so it cannot happen
again.

### 8 · One file is stored twice at 3.5 MB

`finder.json` and its backup are both in the saved history at 3.5 MB each. The
loader can rebuild it, so it could be kept out of the history.

### 9 · Two servers serve the project

A small Python server and the main web app. The docs say the app is the
deliverable. Make that obvious on the front page, so nobody tests the wrong one.

### 10 · The dictionary must chase the data it describes

The `data/` dictionary is new, and nothing checks that it still matches the
files. One small check — "every field named in the files is explained in the
dictionary" — would keep it honest.

## The five things I would do next

1. Pin the counting rules to the three known numbers and fix the counters that
   disagree.
2. Decide which file holds what, so the sandbox page draws again.
3. Refresh the saved copy at the start of every check.
4. Save the unsaved files, then send the three versions to the backup copy.
5. Split the three slow checks from the logic they test.

## In one sentence

What is rare here is not the maths — it is that the maths is *guarded*: every
file says what it is, every claim carries its command, every fault has a test
that keeps it fixed. The risks all sit where two systems meet (the copy and the
check, the page and its builder, one session and another), and each one is a
decision that is already written down and only needs to be made.
