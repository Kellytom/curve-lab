---
title: Where the data lives
---

The curves, their names, their ratings and their settings live in one SQLite
database. The JSON files are a seed and an export, not the place edits happen.

## The record

`app/prisma/dev.db` — one file, reached through Prisma. It is not committed; a
fresh clone creates it from the schema and fills it from the JSON index.

| table | one row is | the fields that matter |
|---|---|---|
| `Curve` | a curve | `uid`, `name` (unique), `family`, `lists`, `aliases`, `starred`, `candidate` |
| `Note` | the human edits to a curve | `name`, `importance` 0–10, `rotation`, `pieces`, `borderUid` |
| `CurveSet` | a composite | `innerUid`, `borderUid`, `rotation`, `pieces`, `perSide`, `importance` |
| `Star` | a finder star | `name`, `note`, `spec` |
| `PlateStar` | a starred plate | `id`, `note` |
| `User` | a directory entry, not a login | `id`, `name`, `email`, `role`, `notes` |

`Note.uid` is the same uid as `Curve.uid`; one curve has one note. A set points
at its inner curve and, when it differs, at its border curve. A curve in several
lists is still one `Curve` row — the lists are names inside one JSON array.

## What is derived

- `workbench/curve-registry.json` is the **seed**: every curve, its rows, its
  lists and the default set. The migration copies it in.
- `workbench/curve-notes.json` and `workbench/finder-stars.json` are **exports**
  kept for the Python tools and for a backup you can read. The database is the
  record; an export can be thrown away and rebuilt.
- `app/public/figures/` and `app/public/curves/` are **renders**, regenerated by
  `scripts/curve_pngs.mjs` and `scripts/curve_plain.mjs`.

## Backups

A snapshot is taken automatically when the app starts (`npm run dev`), before a
build, and before the migration. Each one is a complete copy made with SQLite's
own `.backup`, and each is checked with `PRAGMA integrity_check`.

- Snapshots live in `state/backups/db/`, the last 20 are kept, and the database
  runs in WAL mode.
- `npm run backup` takes one now; `npm run restore` puts the newest back, and
  copies the current database aside first.

## Commands

```sh
cd app
npx prisma db push          # create or update the tables from the schema
node scripts/migrate.mjs    # copy the JSON index in, once, with counts
node scripts/check-db.mjs   # prove the database still matches the index
npm run backup              # a snapshot now
npm run restore             # the newest snapshot back
npx prisma studio           # optional: a browser view of the tables
```

## Why this stack

SQLite for the file, Prisma for the client and the schema. A save is a
transaction, a duplicate uid is refused by the database, and the schema is
written down in `app/prisma/schema.prisma` rather than inferred from code. The
previous design wrote JSON by hand and could lose a name when a save failed;
that is the fault this replaces.

The JSON index stays because the Python engine and the audits read it without a
Node database driver, and because a plain file is the right shape for an export.
