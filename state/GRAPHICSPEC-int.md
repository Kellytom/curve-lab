# GRAPHICSPEC — how a curve is drawn, everywhere

One drawing spec for every curve in the collection, for the book and the documentation. It
names the module that does each step, so a change is made once and the plate, the figure and
the page move together.

## What a curve record must carry

| field | meaning | lives in |
|---|---|---|
| `speedX`, `speedY` | the speed rows, power basis, whole numbers | `workbench/curve-registry.json` → `Curve` |
| `path` | the drawn stations, for a curve stored as a path | same record |
| `transform` | `{ degrees, matrix, scale, exact }` — the orientation | record; `Note.transform` |
| `widthPct`, `plus`, `minus`, `profile` | the character rails | `Note` (the database is the record) |
| `formula` | `{ plain, rational, parameter, use, search }` | record |
| `grid` | `1/G`, exact | record |

Nothing draws without a record: the plate is derived from the record, never typed.

## The steps

**1. Spine and character rails.** `workbench/plate_math.js`, `group(row)`.

These are **character offsets, not parallel offsets**: the rail's shape comes from
`widthPct`, `plus`, `minus` and the profile (`bow`, `s`, `taper`) — the same `rail()`
function the sandbox draws with — so the two sides differ and each side bends with its own
sign. A parallel offset would be the same curve on both sides at every station; that is not
what is drawn. Pinned by `tests/js/plate-character.test.mjs` (changing `plus` moves the + rail,
changing `minus` does not; changing the profile moves it).

```
paths[0]        the spine
paths[1]        the + character rail
paths[2]        the − character rail
paths[3..]      the joins from each spine end to each rail end
```

The rails are the same maths the sandbox uses — `workbench/ph_nth_panels.js`
(`characterRail`) is the live version — so a plate and a sandbox panel of the same curve
agree. A rail that would fold is halved until it does not; at the 0.2 % floor the plate is
spine-only and the note says so. **No stored width means the module's default (1.5 %), never
zero**: zero puts the rails on the spine and the bands have no area.

**2. Turn.** `scripts/lib/plate-frame.mjs`, `turn(points, degrees)`.

The record's `degrees` is applied **clockwise on screen**, the same direction as the desk's
`rotate(45deg)`, so a plate matches the card it came from. The stored matrix stays the exact
one (`[[1,1],[-1,1]]` for 45°, scale `√2`); the plate only needs the angle.

**3. Frame and crop.** `scripts/lib/plate-frame.mjs`, `frame(x0, x1, y0, y1, longSide)`.

The box is the point set plus 1.2 % margin; the canvas long side is exactly the requested
pixels (3000). **+y is up**: a larger `y` in the data is higher in the image. Pinned by
`tests/js/plate-frame.test.mjs`.

**4. Tones.** From the spine and the two rails, in this order:

| area | fill |
|---|---|
| between the right rail and the spine | `#8a8a8a` — dark grey |
| between the left rail and the spine | `#e2e2e2` — light grey |
| the spine | stroke `#2b2b2b` |
| the rails | stroke `#3a3a3a` at 0.6 × the spine width |

Every band is the spine walked out and the rail walked back, closed — one path per band, so a
folded rail never fills the wrong side. **No colour anywhere**: two greys and black print as
two tones.

**5. Stroke.** 3.5/1000 of the long side (10.5 px at 3000), round caps and joins.

**6. Raster.** `scripts/print_plates.mjs` writes the SVG, then Chrome (Playwright) renders
it at the canvas size; `scripts/lib/png-dpi.mjs` stamps the PNG's `pHYs` chunk to **300 dpi**.
No PIL, no ImageMagick: the browser is the rasteriser, so the plate is the SVG.

**7. Ground and text.** White `#ffffff`. **No text on the plate** — no title, no axes, no
legend; the name and the record are on the page that lists it, and in `plates.json`.

## Where the result lives

- `book/print/<uid>.png` and `<uid>.svg` — one pair per curve, regenerated by
  `node scripts/print_plates.mjs --all` (`--missing`, `--only uid,uid`, `--tone=one|two`).
- `app/src/pages/plates.astro` — every curve in one list; clicking a thumbnail opens the
  plate; the card links the PNG, the SVG and the record's formula and turn.
- `app/src/pages/api/print-plate/[uid].js` — serves the pair; the uid is checked against
  `^c-\d{4}$` before a path is built.
- The PNGs are **not in git** (40 MB, regenerable): `book/print/` is ignored.

## Checks that fail when the spec stops being true

| rule | check |
|---|---|
| +y is up; a turn is clockwise; the long side is exact | `tests/js/plate-frame.test.mjs` |
| the page lists every record and serves every plate | `app/scripts/check-pages.mjs`, `/plates/` in the 19-page run |
| the rails and the bands come from `plate_math` | the export prints `rails N` per plate; `N ≥ 2` means bands were drawn |
| the database and the seed agree | `node app/scripts/check-db.mjs` |

## Open

- **Path records have no rails yet.** The hybrids, wonkies and doubles are stored as paths;
  `plate_math` builds rails from speed rows, so those plates are spine-only. A path-based
  rail is the one missing piece, and it is the same gap named in `state/SPEC-hybrids-int.md`.
- **The turn is applied to the drawing, not the data.** The record keeps its own coordinates
  and the matrix; the plate turns the picture. A future "clean formula" would write the turn
  into the parametric form instead (state/PLAN-int.md, next 1).
